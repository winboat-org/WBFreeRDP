# WinBoat #558 / PR559: separate the frame cap from the tuning bundle

On this Windows 11 / Helios VM, `DWMFRAMEINTERVAL=15` clearly raises the effective
RemoteApp frame rate. The other fourteen settings in PR559 have not demonstrated
a repeatable additional benefit in these tests. A narrow, reversible frame-cap
option is better supported by the evidence than importing the whole bundle as
a default. This investigation leaves the original fifteen values/absences restored.

The reviewed PR head is `cf3bb6d3f92c5c6fcd4f025d85ad7d68fe5bff4e`.
[Issue 558](https://github.com/winboat-org/winboat/issues/558) and
[PR559](https://github.com/winboat-org/winboat/pull/559) include both favorable
reports and reports of poor behavior. These experiments do not establish the
cause of another user's artifacts or reproduce their precise setup.

## Measured result

| Workload | Original settings | Frame-cap setting only | Full PR bundle |
|---|---:|---:|---:|
| Numbered GDI tiles, moving content | about 31.7 FPS | 54.5–57.0 FPS | 55.2–57.2 FPS |
| Simple numbered GDI tiles | about 31.7 FPS | 58.7 FPS | 57.3 FPS |
| Native 1280×720 moving gradient | about 31.6–31.7 FPS | 41.2–53.8 FPS, codec-dependent | 41.7–53.2 FPS, codec-dependent |

Restored settings returned to about 31.7 FPS. The full measurements, sample
counts, gaps, codec counts and GPU activity are in
[the measurement ledger](pr559-measurements.md), with CSV and JSON alongside it.

The native test revealed an important confounder: Windows sometimes sent
AVC420 and sometimes used Progressive/ClearCodec for the same pattern and
advertised capabilities. For example, the first frame-only software run delivered
41.2 FPS with AVC420, while a later frame-only software repeat delivered 52.6 FPS
with no AVC420. Full-bundle software runs around 51–53 FPS likewise used the
non-AVC path. Comparing those runs without their codec counts would falsely
suggest an effect from the extra registry settings. The mixed-codec runs do not
isolate decoder speed either.

VAAPI was actually exercised in selected repeats, as shown by positive AMD
DRM video-decode counter deltas and AVC420 commands. Other runs configured the
same overlay but never received AVC420, so their initialization log messages
are not evidence of hardware decoding. `/gdi:hw` is X11 rendering, a separate
choice from H.264 decoding.

Invalid frame markers also occur in the baseline. They may reflect partial
updates, sampling during presentation, or lossy codec boundaries; they are
rejected rather than counted as frames. No backwards valid frame numbers were
seen. Three isolated intervals over 100 ms occurred across the full-bundle native
runs (one in the first software case and two in repeats); the short tests do not
establish a systematic full-bundle stall problem.
They also do not rule out problems in long sessions or other applications.

## What the fifteen settings actually mean

| Setting in PR559 | Assessment |
|---|---|
| `DWMFRAMEINTERVAL=15` | Documented way to raise the RDP frame-rate limit to 60 FPS; requires a restart. It changes a ceiling, not a guaranteed delivery rate. This is the setting with a clear local benefit. |
| `OverlayMinFPS=0` | Removes DWM's minimum-rate requirement for assigning swap chains to hardware overlay planes. It does **not** disable overlays or directly set the RDP frame rate. Effects can depend on hardware/driver support. |
| `SystemResponsiveness=0` | MMCSS documentation says values below 10 are clamped to 20. Zero does not mean reserving zero CPU for background work. Original local value was 20. |
| `FlowControlDisable=1` | Historical TermDD control that disables its bandwidth-allocation algorithm in favor of FIFO. The TermDD service key did not exist on this Windows build before the test; applicability here is unproven. |
| `FlowControlDisplayBandwidth=16` | Historical relative display weight, not a bandwidth measurement. |
| `FlowControlChannelBandwidth=144` | With the previous value, the historical ratio would heavily favor virtual channels if allocation were enabled; the bundle simultaneously disables that allocation. |
| `FlowControlChargePostCompression=0` | Historical default accounting mode, using pre-compression size. No independently demonstrated benefit here. |
| `InteractiveDelay=0` | Protocol-driver configuration describes this as write delay during active input. Original value was 50. The animation benchmark does not isolate interactive input latency. |
| `DisableBandwidthThrottling=1` | SMB client tuning under LanmanWorkstation; it does not directly configure RDP graphics. No file-share benchmark was performed. |
| `DisableLargeMtu=0` | Allows larger SMB requests; not an RDP frame-rate control. |
| `bEnumerateHWBeforeSW=1` | Selects hardware rendering for RDS sessions. Current policy text already defaults to hardware outside an RD Session Host deployment. A rendering policy alone is not evidence of hardware encoding. |
| `fEnableVirtualizedGraphics=1` | Legacy RemoteFX compatibility policy. Current policy text restricts its codec effect to RDP 7.1 clients. It does not enable a generic modern GPU acceleration feature for this RDP 10 client. |
| `SelectTransport=2` | Allows UDP or TCP. It does not force TCP, and matches the normal automatic choice. The test used the existing local TCP mapping. |
| `AVCHardwareEncodePreferred=1` | Requests server H.264 hardware encoding, falling back to software on failure. Client VAAPI decode activity does not establish that the guest encoded on the GPU. This experiment did not trace the guest encoder. |
| `VGOptimization_CaptureFrameRate=60` | **Wrong value domain:** the guest's shipped ADMX defines this legacy RemoteFX setting as an enum: highest=1, medium=2, lowest=3. The value is not a literal FPS count. Writing 60 is outside the defined policy choices. |

## Reproduction and limits

The source fixtures are `tests/frame-probe.cs` and `tests/frame-probe-native.c`.
They encode an increasing frame number with complementary black/white markers.
`tests/sample-frames.py` reads actual X11 window pixels around 200 times per
second and counts distinct valid numbers. It measures visible updates, not
repaint requests, CPU usage, or a server's claimed FPS.

`scripts/run-pr559-matrix.py`, `run-pr559-native-matrix.py` and
`repeat-pr559-native.py` launch only the test application. Settings changes are
followed by a guest restart. Their `finally` paths restore the saved settings,
restart, and verify all fifteen original values/absences, including removal of
the originally absent TermDD key when empty. The alternating native repeats use
fresh boots in full/frame-only/full/frame-only order and 30-second samples.
The earlier cases use 20-second samples with a three-second warm-up.

Tests use the reviewed resize/resume client built against FreeRDP 3.30.0,
Windows 11 build 26200 with the installed Helios driver, the local WinBoat TCP
forward, XWayland, and the host RX 6600. The one-CPU cases also switch to software
GDI, so they are combined stress cases and cannot isolate either change. This
was an active development machine, not a dedicated benchmark host. No packet
loss or WAN latency was injected. No broad driver stability conclusion follows.

There was an investigation-script error before these controlled comparisons:
`New-Item -Force` replaced the WinStations registry tree and temporarily disabled
RDP. Recovery restored service, but ten reconstructed values and original per-key
ACLs cannot be proven identical to the former state. This was our test setup
error, not PR559. The [incident and recovery report](registry-test-incident.md)
documents the limitation. Comparisons above use a fresh post-recovery baseline;
the restored frame rate also agrees with the brief pre-incident baseline.
